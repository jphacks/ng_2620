# ADR-0005 プレビュー合成はアプリ内 WebGL、書き出し合成はサーバー。合成規則は契約として共有する

- 状態：採択
- 日付：2026-10-24

## 文脈
- 前後関係の手修正（P0）は、修正してすぐ結果が見えないと使えない（目標 0.5 秒以内）。サーバー往復（数十秒）では編集にならない。
- 書き出しは元解像度（最大 1920px）で、品質（スーパーサンプリング、アバター同士の z バッファ、時間方向の平滑化）は既存の `avatar_app.py` の合成が持っている。
- Mac → リモート GPU の経路では、フル解像度のレイヤーを全部ダウンロードすると重い（10 秒・1080p・2 人で数 GB）。

## 決定
1. **プレビュー**：サーバーがプロキシ解像度（1080p の素材なら 540x960、[ADR-0011](0011-input-limits-and-resolutions.md)）のレイヤーを作り、アプリがダウンロードしてキャッシュし、**WebGL2 シェーダーで毎フレーム合成**する。
   手修正はシェーダーの入力（ユニットごとの前/後ろのテーブル）を変えるだけなので即時に反映できる。
2. **書き出し**：アプリが手修正（オーバーライド JSON）をサーバーに送り、サーバーが**フル解像度で合成・エンコード**する（`export` ジョブ）。
3. 両者の結果を一致させるため、**合成規則**（どの画素にどのレイヤーを出すか）を契約として 1 つに定義し（[contracts §5](../architecture/contracts.md#5-合成規則composite-rule)）、
   アプリの `domain/composite`（TS の純粋関数＋シェーダー）とサーバーの `domain/composite`（Python）が同じテストケース（固定データの画素比較）を通る。
4. プレビューで許す差：アバター同士の前後は**フレームごとの順序**（サーバーが深度の中央値で決めた順）で近似する。書き出しは画素単位の z バッファ。

## 却下した案
| 案 | 却下理由 |
|---|---|
| サーバーで再合成してプレビューも動画で返す | 修正 1 回ごとに数十秒待つ。編集体験にならない |
| 書き出しもアプリで行う（フル解像度レイヤーを全部ダウンロード） | 経路 2 で転送が重い。Mac に ffmpeg の同梱も要る。品質処理（SSAA、z バッファ、平滑化）を TS で作り直すことになる |
| プレビューに z バッファを持ち込む（人物ごとの深度レイヤーを配信） | 転送量とシェーダーが増える。人物が交差する場面はデモ素材では稀。P2 で検討 |

## 影響
- サーバーは `render` で「プロキシ解像度のレイヤー」を書き出す改修が要る（現行の `avatar_app.py` は合成済みフレームしか保存しない）。[pipeline-integration](../architecture/pipeline-integration.md)
- サーバーの書き出し合成は、手修正を自動の隠れマスクに適用してから既存の合成に渡す（`--hide_override` の追加）。
- プレビューと書き出しの見た目差は「アバター同士が重なる画素」に限られることを、デモ素材で目視確認する（途中のマスクの数値でなく、最終出力の映像で比べる）。
