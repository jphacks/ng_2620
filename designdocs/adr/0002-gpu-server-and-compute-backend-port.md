# ADR-0002 推論は GPU サーバーに分離し、アプリからは ComputeBackend ポートで抽象化する

- 状態：採択
- 日付：2026-10-24

## 文脈
- パイプライン（SAM3、SAM-3D-Body、fusion v2、VRM 描画）は CUDA 前提で、VRAM 数 GB を使う。Mac では動かない。
- 想定する経路は 2 つある：
  1. **Windows ローカル**：アプリと同じ PC の NVIDIA GPU で推論（チームの RTX 5060 Ti 機など）。
  2. **Mac → クラウド GPU**：Mac のアプリから、リモートの GPU サーバーに接続。
- デモは Mac で行う。接続先は「チームの Windows 機をリモート化したもの」になる可能性もある（経路 1 のサーバーを経路 2 として使う）。
- 将来はクラウドのマネージド GPU（Modal 等）やオンプレの専用サーバーも考えられる。

## 決定
1. 推論は **GPU サーバー（Python / FastAPI）** に分離する。ローカルでもリモートでも**同じサーバー実装・同じ HTTP API** を使う。
   - ローカル = `http://127.0.0.1:<port>` で起動したサーバー（Windows ではアプリが子プロセスとして起動、P1）。
   - リモート = トンネル越しの HTTPS、またはクラウド VM。**今回のデモはチームの Windows 機を Tailscale で公開し、デモ用の Mac から接続する**（[ADR-0012](0012-transport-and-auth.md)）。
2. アプリ側は **`ComputeBackendPort`** だけに依存する。実装（アダプタ）は：
   - `HttpComputeBackend`：GPU サーバーの HTTP API（ローカル・リモート共通）。
   - `OfflineComputeBackend`：サーバー無し。同梱プロジェクトを開いたとき・オフライン時。ジョブ投入は「接続してください」を返す（[ADR-0009](0009-demo-resilience.md)）。
   - 開発用には別プロセスの**モックサーバー**（同じ HTTP API、固定データを返す）を `HttpComputeBackend` で使う（F14）。
3. 接続先は**接続プロファイル**（種別・URL・トークン）としてユーザーが登録し、プロジェクトごとに使ったプロファイルを記録する（F03）。

## 却下した案
| 案 | 却下理由 |
|---|---|
| ローカル用とリモート用で別 API（ローカルは IPC など） | 同じ機能を 2 回作ることになる。HTTP にしておけば Windows ローカルもデモのリモートも同じコードで試せる |
| Modal 関数を直接呼ぶ（既存の `modal_body4d.py`） | Modal 専用の SDK 呼び出しがアプリに入る。コールドスタート（数分）がデモ中に出る。将来のアダプタとして残す（サーバー API を Modal の Web エンドポイントで公開すれば同じポートで使える） |
| Colab | 対話用の実行環境で、常駐サーバーとして不安定（接続が落ちる・セッションが切れる）。開発時の検証にだけ使う |

## 影響
- アプリは推論の場所を知らない。プロファイルの切替だけで経路 1 / 2 を変えられる。
- サーバーは GPU 1 枚あたり 1 ジョブずつ実行（[ADR-0014](0014-server-stack.md)）。複数ユーザーの同時利用はキューで待つ。
- 大きなデータ（動画・フレーム）が経路 2 ではネットワークを通る。プレビューはプロキシ解像度のレイヤーだけを取り寄せ、フル解像度の合成はサーバーで行う（[ADR-0005](0005-preview-composite-client-export-server.md)）。
